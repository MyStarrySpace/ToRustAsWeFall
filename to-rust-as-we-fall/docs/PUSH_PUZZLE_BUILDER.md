# Push-Puzzle Builder — mini-Sokoban chambers inside the compositional framework

Design-before-implementation. The proof suite that constrains everything here lives in the session
proofs scratchpad §8 and graduates into this doc's companion tests (S1–S8) when the builder lands.
Nothing below may be implemented in a way that invalidates a numbered theorem; if implementation
pressure contradicts a theorem, the design changes, not the proof.

## What this composes (and what it does not invent)

The push VERB is shipped: `PushTarget` wraps a pushable body into the hover/outline grammar with the
plan-then-commit flow, and `GameState.plan_push_for` / `command_push_object` own legality, planning,
and replay-safe execution. The push_lab chunk already demonstrates the whole mechanical vocabulary a
chamber needs — open push, corridor push, the impossible bent-corridor push (the dead corner), and
crate-as-obstacle planning. A chamber is a COMPOSITION of that verb with walls, goals, a reset
control, and a gate — no new mechanics.

**Dressing is a canon consultation, not an invention.** The GDD names no block-push canon today.
Crate skins, the chamber's civic purpose (per the architecture-is-BUILT law), and all player-facing
names come from the canonical docs at dressing time; this document deliberately uses only the
neutral mechanical vocabulary (crate, goal plate, reset control, gate).

## The two-layer architecture the proofs force

§8.2 (non-monotonicity): push puzzles cannot be validated by the stretch's greedy flood-open
validator, and cannot be generated by generate-and-hope. Two consequences, each a hard layer
boundary:

1. **INSIDE the chamber — constructive generation with a certificate.** The builder plays BACKWARD
   from the solved state (legal pulls + walks, seeded RNG, no wall-clock), and the recorded
   sequence, reversed, IS a step-legal solution (§8.5). Every emitted instance ships its
   certificate in the spec. A bounded BFS verifier (§8.6, exact at mini scale) re-checks every
   instance at generation time — defense in depth against builder bugs — and the certificate is
   replayed through the SHIPPED `command_push_object` in the guard tests (S3), so the model and the
   game cannot drift apart silently.

2. **AT THE SEAM — the chamber is SEALED (§8.7).** The fragment: (i) certified-solvable initial
   state; (ii) a reset control restoring exactly that state (bodies un-stranded to the mouth);
   (iii) gate-out latch as the ONLY cross-boundary effect, no consumables in or out; (iv) chamber
   interior off the stretch spine. Under those four conditions the chamber presents to the stretch
   as a monotone gate with an always-completable producer, so the stretch-level greedy validator's
   completeness theorem applies to the composed level unchanged. P11 falls out: a wedged crate
   costs the walk to the reset, never the run.

## Design decisions

- **D1 — Certificate is spec data.** The pull sequence is stored in the emitted spec (like
  `solution_order` for branch cuts): it is the solvability witness, the difficulty meter
  (`|pushes|` upper-bounds optimal), the hint source, and the regression fixture forever.
- **D2 — Static filters run during generation, not as the guarantee.** Dead-square (§8.3) and
  freeze (§8.4) filters prune the pull walk away from degenerate instances and prune the verifier's
  search. They are SOUND rejectors, never solvability proofs.
- **D3 — Solo chamber.** One body inside at a time, entered through a mouth that queues the party
  (the shipped one-at-a-time law: CrawlTunnel / portal group semantics). Rationale: the certificate
  proves the single-pusher model; party bodies inside the chamber would be obstacles the model does
  not carry (§8.5 precondition), and the cooperative-reservation layer must never refuse a
  certified push. The rest of the party waiting at the mouth is also the fragment's pair-shadow
  story hook, consistent with the held-station fragments.
- **D4 — Reset is a control, not a menu.** A chamber-mouth interactable (INSPECTION type, click-
  gated per the activation law) restores `σ₀` through the data layer as ONE logged command, so
  replay reproduces resets exactly. Reset also cancels any queued push plan (S5 covers mid-plan).
- **D5 — Generation knobs are certificate-derived.** Stage ramp maps to: crate count k (1–4),
  certificate push count, detour factor (pulls that are not immediately-undone), live-cell density.
  The curriculum test extends the existing ramp assertions rather than inventing a parallel system.
- **D6 — Chamber envelope comes from the existing space vocabulary** (room pieces / fragment
  grammar), placed as a spine pocket by the stretch generator exactly like other gated pockets;
  the gate it opens is realized through the same dynamic-blocker seam as branch cuts, so the G1
  greedy validator sees it with no special casing.

## Builder pipeline (to implement, in this order)

1. `PushPuzzleModel` — pure data-layer model + legality (mirrors `command_push_object` exactly);
   canonical state hash. No scene, no nodes.
2. Filters — dead-square (pull-reach from goals), freeze certificate. (S1, S2 red/green here.)
3. `PushPuzzleVerifier` — bounded BFS on the model with filter pruning. (S4.)
4. `PushPuzzleBuilder` — seeded reverse walk with quality knobs; emits {grid, crates, goals,
   certificate, knob readouts}; rejects net-zero and sub-stage instances. (S7.)
5. Certificate replay harness through live headless GameState + `command_push_object`. (S3, S8.)
6. `push_chamber_chunk.gd` — the sealed fragment: mouth queue, reset control, gate latch, manifest
   (components: crates, goal plates, reset, gate; behaviours: each S-guard's flag). Loader wiring
   per the four-point law, picker row at top.
7. Stretch integration — chamber as gated pocket; G1 validator consumes it as a gate.

## Open questions (parked, not blocking)

- Whether chamber solves should feed the run economy (currently NO per D3 sealing — a solve emits
  the gate latch only; any reward would puncture §8.7(iii) and needs its own composition proof).
